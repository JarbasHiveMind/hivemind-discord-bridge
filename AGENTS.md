# AGENTS.md — `hivemind-discord-bridge`

Guidance for AI coding agents (and humans) working in this repository. Read it
fully before making changes. It encodes conventions that are not obvious from the
code and that, if ignored, produce work that will be rejected.

## Repo

Bridges a Discord bot to a HiveMind node: a HiveMind bridge is a satellite
whose input and output are a chat platform instead of a microphone. Inbound
Discord text messages (channels the bot can read, plus DMs) become
`recognizer_loop:utterance` bus messages; the hub's `speak` replies are
posted back into the originating channel or DM. Part of the
[HiveMind](https://github.com/JarbasHiveMind) ecosystem — a protocol for
connecting satellite devices to a hub running
[OpenVoiceOS](https://github.com/OpenVoiceOS). The hub is
[HiveMind-core](https://github.com/JarbasHiveMind/HiveMind-core); the client
library is
[hivemind-bus-client](https://github.com/JarbasHiveMind/hivemind-bus-client).
Sibling bridges with the same shape: `hivemind-telegram-bridge` and the other
chat-platform bridges under the org — check them for prior art before
inventing a new pattern here. Text-only; voice channels are documented in the
README as a deliberately unimplemented future direction, not a gap to fill
casually.

## Layout / build / test

- Package module: `hivemind_discord_bridge/`. Tests live in `tests/` (check
  before adding — do not create a second test directory).
- Set up a throwaway environment inside your clone; never touch a shared venv:
  `python3 -m venv .venv && VIRTUAL_ENV=$PWD/.venv uv pip install -e ".[test]" --prerelease=allow`
- Run the suite in the foreground: `python3 -m pytest tests/ -q`. It mocks
  both `discord.Client` and `HiveMessageBusClient`, so it runs without a live
  bot token or hub — that also means it cannot catch a real handshake hang or
  a real Discord gateway break; treat it as a shape/wiring check, not a
  live-behaviour guarantee.
- `uv`, never `pip`. If latest prereleases fail to install or resolve, that is
  a bug to FIX at the source, not to work around with a pin downgrade.

## Working agreement (org-wide law)

- **Git identity is always** `JarbasAi <jarbasai@mailfence.com>`. Never set a
  per-repo override.
- **Never push `dev` or `master`.** Work on a feature branch and open a
  **draft** PR into `dev`. A human merges. You do not merge your own PRs.
- **Never merge or modify `Release X → master` PRs.** They are the maintainer's
  stable-release mechanism, generated by automation.
- **One commit per PR** (squash before pushing). Conventional commits; `feat:`
  only for a user-visible new capability. `fix:`, `docs:`, `chore:`, `ci:`
  otherwise.
- **Disclose AI authorship.** Every PR/issue/comment an agent writes carries, at
  the top: `> 🤖 Auto-generated by <model> via Claude Code — NOT human-reviewed.
  Verify before acting.` PR bodies are plain human prose (3–6 short paragraphs),
  no tables or section-symbol spray.
- **Never edit someone else's** issue, PR description, or comment. Add a comment
  instead; on your own PRs, edit the body rather than piling on comments.
- Keep durable text (README, docs, PR bodies, comments) timeless and standalone:
  no dates, no "currently/now/new", no meta-commentary about the edit itself.
- No scratch files, committed virtualenvs, `__pycache__`, `.pyc`, `.egg-info`,
  or build artifacts in a PR. `git show --stat` shows only intended files.

## Dependencies

- **Floor pins only** (`>=X.Y.Za1`), bumped when a feature or fix is actually
  needed — with a one-line comment saying why. No upper caps unless a specific
  released version is genuinely broken (say which and why).
- **No lockfiles, ever.** Target the latest alphas (`--prerelease=allow`).
- Everything in `pyproject.toml`/`requirements.txt` (deps, metadata, version).
  Never install from git — depend on a published PyPI alpha.
- Apache-2.0. Do not add GPL/AGPL dependencies.

## Tests

- Adversarial by default. A regression test must **fail before the fix and pass
  after** — prove it by reverting only the source (`git apply -R`, never
  `git stash` across worktrees) and watching the test flip.
- Tests must be mutation-proof: gutting the feature must fail the test. A test
  that only asserts a mock was called, without asserting the real behaviour, is
  weak — note it.
- Never skip a test because an optional dependency is missing.
- CI green is permission to review, not to merge. A non-trivial change gets an
  adversarial review before it lands.

## Repo-specific rules

- **Composition, not inheritance.** `HiveMindDiscordBridge.__init__` builds
  (or accepts an injected) `HiveMessageBusClient`, but `HiveMessageBusClient`
  never opens a connection in its own `__init__`. The actual connection
  happens once, in `connect_hivemind()`, called from `start()`. Never add a
  second call to `connect()`, and never call `run_forever()` in addition to
  it — `connect()` already starts and owns the reconnect worker thread for
  as long as the process runs.
- **`connect()` must bound `handshake_max_retries`.** The
  `hivemind-bus-client` floor is `>=1.0.13a1`; that client's own default for
  `handshake_max_retries` is `None`, meaning retry forever. `connect_hivemind()`
  currently calls `self.client.connect(site_id=self.site_id)` with no bound,
  so against a stalled or unreachable hub (down, wrong password) it hangs
  indefinitely instead of failing fast. This is a standing requirement, not
  yet met by the code: any change touching `connect_hivemind()` should add an
  explicit finite `handshake_max_retries`, exposed as a constructor/CLI
  parameter so operators can tune it, rather than leaving the unbounded
  default in place.
- **The hub owns ACL, not this bridge.** A freshly registered HiveMind client
  is denied every message type until an admin runs `hivemind-core allow-msg
  recognizer_loop:utterance <client_id>` (and usually `speak`). This bridge
  has no way to grant itself permissions and must not try to work around a
  denial locally — a silently dropped message on the hub side is the hub
  doing its job, not a bug here. `--allowed-channel` is a separate,
  bridge-side filter over which Discord channels may originate traffic (DMs
  are always accepted regardless); it is not a substitute for hub-side
  message-type ACLs.
- **Rejected credentials must fail fast.** Once `handshake_max_retries` is
  bounded (see above), a wrong access key/password turns into a clean
  failure instead of a bridge that spins forever looking connected. Do not
  add retry/backoff logic on top of `connect()` that defeats this.
- **Forward upstream responses verbatim.** `handle_speak()` forwards
  `message.data["utterance"]` to Discord unmodified; do not reformat,
  truncate, or add bridge-specific decoration to hub-authored text. The one
  exception is the fixed fallback line on `hive.complete_intent_failure`,
  which is bridge-authored by design because the hub sent no utterance to
  relay.
- **Thread safety.** `speak()` runs on the HiveMind bus's own thread, never
  on the asyncio loop `discord.py`'s `Client` uses. Any new HiveMind →
  Discord path must go through `asyncio.run_coroutine_threadsafe` the same
  way (see `speak()` / `_send()`) — a direct `await` from the bus thread
  will raise or silently no-op depending on timing.
